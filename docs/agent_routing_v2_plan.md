# 智能客服回复链路 V2 方案（强模型优先 + 保留本地兜底）

本文档用于定义下一阶段智能客服链路升级方案。目标是在保留现有可用能力的前提下，构建更适合强模型的路由与执行框架，同时持续支持本地模型兜底。

## 1. 目标

1. 项目先成为一个高质量 RAG 系统：问答准确、可解释、可控、低幻觉。
2. 在对话中完成系统操作：下单、查单、取消、改址、投诉、资料修改等。
3. 回复风格更人性化：亲切、温暖、自然，不暴露内部术语。
4. 保留本地模型链路用于离线/降级，不阻断业务。

## 2. 总体策略

采用“双路由 + 单执行内核”：

1. Action Lane（操作通道）
- 处理写操作与事务类请求。
- 模型负责理解，后端规则负责强校验与执行。
- 执行前必须确认（confirm gate）。

2. RAG Lane（知识问答通道）
- 处理价格、安全、规则、流程、年检等问答。
- 统一检索入口，带检索质量门槛与 query 改写。
- 低置信时先澄清再回答。

3. Legacy Fallback（本地模型兜底）
- 保留现有 Ollama/规则兜底链路。
- 强模型不可用时自动降级，保证业务可用。

说明：业务执行内核（tools + 后端规则 + 状态机 + 审计）只保留一套，不分叉。

## 3. 是否还需要“缺槽/匹配”

需要，但策略调整为“模型优先 + 规则兜底”：

1. 保留的规则（硬约束）
- 订单状态机、支付前后关系、取消/改址时限、手机号/时间窗合法性、权限校验。

2. 弱化的规则（可下沉给模型）
- 大量意图关键词匹配与复杂正则拼装。
- 由强模型输出结构化 ActionPlan，再经后端校验。

3. 缺槽收集策略
- 一次只问一个关键缺槽。
- 优先自动带出默认地址/联系方式/历史偏好，再让用户确认是否沿用。
- 收齐后给“用户可读摘要”而非字段清单。

## 4. V2 链路（建议）

## 4.1 输入阶段

1. 接收用户消息 + 账号上下文 + 最近对话记忆。
2. 先做轻量分类：
- 明确操作意图 -> Action Lane
- 其他 -> RAG Lane

## 4.2 Action Lane

1. 强模型生成 `ActionPlan`（结构化）：
- `intent`
- `slots`
- `confidence`
- `missing_slots`
- `confirm_required`

2. 后端策略引擎校验：
- 参数完整性
- 权限与归属
- 业务规则可执行性

3. 缺槽则追问；齐全则生成确认摘要。
4. 用户明确“确认”后调用工具执行。
5. 返回结果 + 下一步建议（可查进度/继续办理）。

## 4.3 RAG Lane

1. Query 改写（结合最近上下文）。
2. 域路由（建议至少三类）：
- `biz`（价格/规则/流程/发票/年检政策）
- `safety`（安全规范/应急处置）
- `personal`（用户侧订单与资料解释）

3. 检索与过滤：
- `top_k`
- `min_score`
- `min_hits`
- OOD（越域）判断

4. 命中达标 -> 证据约束生成。
5. 命中不足 -> 先澄清问题，不强答。

## 5. 人性化回复规范（新增强约束）

智能客服回复必须“亲切、温暖、自然”，并满足：

1. 不暴露内部术语
- 禁止出现 `payload`、`missing_fields`、`slot`、`json`、`tool` 等字样。

2. 用户可读优先
- 避免“字段=值”格式。
- 使用自然口语表达，减少模板腔。

3. 情绪与礼貌
- 对求助、投诉、紧急问题先共情一句，再给可执行步骤。
- 语气专业但不生硬。

4. 关键场景话术要求
- 下单收集：每轮只问一个关键问题。
- 确认阶段：先摘要，再提示“确认/修改/取消”。
- 完成阶段：明确结果、时间、下一步入口。
- 安全场景：优先风险提示与应急步骤。

5. 风格个性化（可控）
- 基于用户偏好保留 `neutral / warm / direct` 三档。
- 默认 `warm-neutral`，高压场景切 `direct`。

## 6. 记忆与上下文策略

1. 会话历史是账号资产，不依赖页面刷新。
2. 保存两类信息：
- 对话历史（可回放）
- 结构化偏好（默认地址、常用规格、语气偏好、最近意图）

3. 使用原则
- 只用于提升理解与减少重复提问。
- 涉及写操作仍需当轮确认。

## 7. 可观测性与评估指标

1. 质量指标
- 意图识别准确率
- 缺槽追问轮数
- 一次确认通过率
- RAG 命中率与拒答正确率
- 用户主观评分（自然度/温暖度）

2. 效率指标
- 首 token 延迟
- 端到端响应时延
- 工具调用成功率

3. 安全指标
- 误执行率（未确认执行）
- 规则校验拦截率
- 幻觉率（无依据答复）

## 8. 分阶段落地（建议）

1. Phase A（先稳）
- 保留现有链路，新增强模型主路由开关。
- 强模型仅用于问答与话术优化，操作仍走现有规则流。

2. Phase B（提效）
- 上线 `ActionPlan` 结构化解析。
- 统一缺槽追问模板与确认摘要模板。

3. Phase C（强化）
- 完整启用三域 RAG + 质量门槛 + 澄清机制。
- 加入人性化回复评分与回归测试集。

4. Phase D（收敛）
- 保留本地模型 fallback。
- 默认强模型；按 SLA/成本动态切换。

## 9. 风险与边界

1. 不改主业务规则归属：所有业务约束仍在后端。
2. 不让模型直接“决定执行”：模型只提议，系统才执行。
3. 不因追求自然话术牺牲准确性与可审计性。

## 10. 本阶段结论

1. 不建议继续重投入“弱模型专用规则堆叠”。
2. 建议保留现有本地链路作为兜底。
3. 以强模型为主，推进“双路由 + 单执行内核 + 人性化回复”的 V2 架构。
